# KidsProgress v2.5 — Rebuild Plan

Generated 2026-05-31 via parallel-discovery + design-panel workflow (27 agents).
Companion: [2026-rebuild-plan.md](2026-rebuild-plan.md), [frontend-restoration-plan.md](frontend-restoration-plan.md).

## Product overview

KidsProgress helps parents (one account per family) plan a calm, age-appropriate study and chore routine for their kids aged 5–15, and gives kids a friendly, focused runner to actually do that work on a shared family tablet. Parents pick from a library of task templates — math drills, writing exercises, reading logs, generic checklists — configure the parameters (questions per round, minimum words, AI feedback on/off), and assign them to one or more children on a date or recurring schedule. Kids land on a Khan-Kids-style profile picker, tap their face (optionally with a PIN), and see only today's plan in their portal — no streak guilt, no Duolingo-style pressure mechanics, no payment surfaces.

Under the hood it's a single multi-stage Docker image deployed to a Synology DS216+II. Node 22 + Fastify 5 + Zod + Drizzle (SQLite) on the server; React 19 + Vite + TanStack Query + Tailwind + i18n (en/zh) on the client. Templates are plugins (built-in only at launch — math, writing, reading-log, generic) with a typed lifecycle the executor dispatches by id. Scheduling is template + assignment + lazy-materialized instances: virtual occurrences are computed on read from the assignment's RRULE history, and only become a real DB row the first time the child taps Start or the parent overrides — one transactional `materialize()` chokepoint. AI is restricted to writing evaluation and recommendation through one server-side `lib/gemini.ts` wrapper that scrubs PII, fences user content in `<user_content>`, and enforces a per-child daily token cap.

## Decisions reached (from design panel)

- Account model: SINGLE parent account (email+password) + N child profiles (avatar + optional PIN) + family-scoped trusted devices via a device_children join table. Three role-tagged JWTs (parent, child, child-readonly). Optional parent-portal PIN re-gates /parent from a trusted device; optional per-child PIN with 5-in-15min lockout gates child login; parent-issued one-time reset code recovers a forgotten child PIN without exposing it. Replace full dateOfBirth with birthYear (PII reduction). KEEP v2's tokenHash + refresh-token rotation + audit log; RESTORE v1's device→many-children pattern (one tablet trusts the whole family).
- Templates: first-class task_templates table with handlerId + schemaVersion + opaque JSON config validated by an in-process VERSIONED handler registry (packages/shared/src/handlers/). Assigning a template inserts task rows with sourceTemplateId + templateSchemaVersion + immutable templateConfigSnapshot. AI metadata (prompt template, response schema, budget slot) lives on the handler manifest, not per-template columns. Per-handler-version migrateFromPrev() means schema evolution is code-only. Startup invariant assertAllPersistedVersionsRegistered() refuses to boot if the DB references an unknown (handlerId, schemaVersion).
- Plugins: single TemplateModule with five typed generics (config/execution/payload/detailed/measured/llmAnalysis), four view slots, declarative tools.attachable. <TemplateRuntime view=... templateId=.../> is the ONLY place doing unsafe casts; hosts never import a concrete module. Tools (Timer/Note/Calculator) live in a SEPARATE parallel registry; host owns tool state via task_sessions.toolStates (single source of truth — drop legacy localStorage 'execution-${taskId}' blob and per-tool autosave). Calculator uses mathjs (not new Function); Timer uses a ref (not elapsedSeconds-in-deps). v1 hardcoded 'tool.id === "note"' placement is replaced by declared placement: 'main'|'sidebar'.
- Scheduling: template + assignment + lazy-materialized instance. Calendar reads run an expander over (assignment.rrule × exceptions); instances are written ONLY when something happens to an occurrence (start, save-progress, complete, skip, override) via one transactional materialize() chokepoint with uniqueIndex(assignmentId, originalDate) as the idempotency primitive. Rule history is a linked list inline on task_assignments (effectiveFrom/effectiveUntil/replaces/replacedBy) — no tail rewrites on pattern changes. recurrence_exceptions is a side table (NOT embedded array) keyed by (assignmentId, occurrenceDate) with actions {skip, reschedule, override, materialized}. Use rrule.js (audit pitfall: never hand-roll RRULE). CalendarKey discriminated union — no 'templateId_YYYY-MM-DD' string ids. School-day strategy is a deferred post-filter, not a custom FREQ.
- Visual: KidsProgress Design System (KPDS). One token spine (packages/shared/src/design/tokens.ts → generated tokens.css + Tailwind theme), TWO themes selected by route-level layout via data-theme="parent|child" attribute. Parent: stone+indigo neutral, no gradients, no mascot, fast+base motion only, density tuned for tables. Child: amber+violet with five gradient chips restricted to TaskTile bg + TodayHero ring, larger type, springs on tile press, sub-theme via data-age="younger|older". Five illustrations restricted to named surfaces (empty/all-done/celebration/auth/hero); icons via @tabler/icons-react everywhere else. Hard 'never' rules encoded in .claude/skills/design-system/SKILL.md: never red/animation/sound on a failed kid action; never numeric streak (only opt-in growing-plant glyph, never animates on break); never mascot/gradient/celebration in parent portal; never raw hex in components. Parent dark mode + animation polish deferred to Phase 3 post-launch.

## Plugin model
Templates are plugin modules registered in a static in-tree `Map<id, TemplateModule>` at `apps/web/src/features/templates/_shared/registry.ts`. Each plugin exports `{ id, version, handlerType, schemas:{config,execution,payload,detailed,measured,llmAnalysis}, defaultConfig, SettingsEditor, TaskExecutor, AnalysisView, AttemptView, tools, i18n, hooks }`. Backend mirror at `apps/api/src/modules/kinds/<id>/handler.ts` implements `{ validateConfig, prepareExecution, processCompletion, shouldAutoComplete, isCompleteByAttemptCount }`. A `<TemplateRuntime view=... templateId=... />` dispatcher is the ONLY place performing unsafe casts. Versioned via `(handlerId, schemaVersion)` with pure `migrateFromPrev(prev)=>next` and a `assertAllPersistedVersionsRegistered()` startup invariant.

Tools (Timer, Note, Calculator) live in a parallel registry at `apps/web/src/features/execution/tools/`. The executor host owns tool state via `task_sessions.toolStates` (one writer); plugins receive a `ToolContext` bus, never a direct tool import.

## AI integration
All Gemini traffic funnels through `apps/api/src/lib/gemini.ts` (already scaffolded at commit `21fa3ad`). Single chokepoint enforces (a) per-child daily token cap (default 5000) by aggregating `llm_logs` for `(childId, dateInChildTz)`, (b) PII scrub: child display name replaced with placeholder, DOB never sent (only `birthYear`/age bucket), (c) prompt-injection fence: all user-supplied text wrapped in `<user_content>…</user_content>`, system prompts contain no user text, (d) structural validation of JSON responses against per-handler Zod (e.g. `WritingLlmAnalysisSchema`). Wrapper exposes `gemini.complete({ slot: 'writing-eval'|'math-hint'|'none', prompt, responseSchema, childId, ... })`. AI metadata (prompt template, response schema, model, temperature, maxTokens, budgetSlot) lives on the handler version manifest, not on per-template rows. Only on/off switch on the template is `aiAssistEnabled: boolean`. Writing eval + recommendation are the only AI surfaces at v2 launch; chat is explicitly out of scope.

## Auth + identity model
Single parent account (`users`) + child profiles (`children`) + family-scoped trusted devices (`devices` + `device_children` join). Role-tagged JWTs: `parent`, `child`, `child-readonly` (view-as-child). Optional parent-portal PIN (`users.parentPortalPinHash`) re-gates `/parent` from a trusted device; optional per-child PIN with lockout (`children.failedPinAttempts`, `lockedUntil`) gates child login; parent-issued one-time reset code (`pinResetCodeHash`) lets parents recover a forgotten child PIN without learning it. Default-deny Fastify `preHandler` on every route — `{ public: true }` is the only opt-out.

# Account model decision: Single parent account + child profiles + family-scoped trusted devices

## 1. Identity model

Three entity types; two are JWT subjects.

- **User** (parent) — one credentialed row per family. Email + argon2id password. Optional `parentPortalPinHash` (4–6 digits) as a second factor re-gating `/parent-portal` from a trusted family device. Role in JWT: `'parent'`.
- **Child** — profile owned by the family. Display name + avatar + optional `birthYear` (NOT full DOB — PII reduction vs v1). Optional 4-digit PIN. Role in JWT: `'child'`.
- **Device** — a registered family tablet/phone. Bound to the family, with an explicit join table listing which children it can show (default: all). Token stored only as hash.

Industry-norm rationale: matches Khan Kids, Greenlight, Family Link, OurHome — the entire 5–15 shared-device segment. Matches v1, which already shipped this shape and is the user's stated preference.

### templates

**Winner:** hybrid

**Reasoning:** Proposal 1 is the structural winner: it matches the existing v2 schema philosophy (single JSON `settings` blob on `tasks`, route-layer Zod validation) and the rebuild plan's bias for small, ship-soon increments. I'm picking Proposal 1's table shape and write path, blended with Proposal 3's versioned handler registry, migrate-on-read, and AI-as-handler-metadata; I'm rejecting Proposal 2's per-kind satellite tables outright.

**Final design:** # Hybrid Scheduling Design — Template + Assignment + Lazy-Materialized Instances

## 0. The three concepts (and only three)

- **`task_templates`** — the WHAT. Parent-owned, child-agnostic. Title, kind, plugin settings, AI flags, defaults.
- **`task_assignments`** — the WHO/WHEN/HOW-OFTEN. Binds one template to one child for a date range with an RRULE (or a one-shot date). Append-only linked-list history so past dates always derive from the rule that was in effect on that date.
- **`task_instances`** — a per-occurrence row, written ONLY when something actually happens to that occurrence (start, save-progress, complete, skip, parent override). For occurrences nothing has happened to yet, there is no row — the calendar synthesizes them virtually from `(assignment.rrule × exceptions)`.

Plus two supporting tables:
- **`recurrence_exceptions`** — side table (NOT embedded array) keyed by `(assignmentId, occurrenceDate)`. Holds `skip` / `reschedule` / `override` rows. Also gets a `materialized` row written automatically every time `materialize()` runs (single source of truth for "this date already has an instance, don't double-emit it").
- **`recurrence_rules`** — optional split if we want the linked-list history off the assignment row. **Decision: keep history inline on `task_assignments` via `replacesAssignmentId`/`replacedByAssignmentId` + `effectiveFrom`/`effectiveUntil`.** One less table; the assignment IS the rule version.

## Risks

- RRULE + DST + IANA timezone correctness is the single highest-risk piece. We're using rrule.js, but DST boundary tests must be written first (Phase 7) before any calendar UI consumes the expander, otherwise we'll be debugging timezone bugs in the WeekView/DayView phase.
- Lazy materialization changes the meaning of 'a task'. The frontend has TWO occurrence types (virtual + instance) wrapped in CalendarKey. If any code path forgets to materialize before mutating, or assumes occurrenceDate is the original date when it's been rescheduled, we get silent calendar duplication. Mitigation: materialize() is the only writer of task_instances, enforced by code review + test that asserts the rule.
- Per-child daily AI token cap default of 5000 may be too low or too high. Default chosen from rebuild plan; first month of real usage may show recommendations exhausting the cap before writing eval gets a turn. Mitigation: token-usage dashboard (Phase 15) and per-child override.
- Synology DS216+II has 1 GB RAM and modest CPU. SQLite + Fastify + rrule.js per-request expansion should be fine for a single family, but a hot month-view query without the LRU cache could spike memory. Mitigation: 92-day read cap at route layer + LRU cache (assignmentId, ruleVersion, yearMonth) from day one of Phase 7.
- Self-hosted variable WOFF2 fonts (Inter, Nunito, Sora, JetBrains Mono) add ~600KB to the initial bundle. Mitigation: font-display: swap, subset to Latin+CJK Common where licensing permits.
- Zh i18n parity check in Phase 15 catches missing keys, but a kid using the app in zh may still hit handler-specific strings the plugin author missed. Mitigation: runPluginContractTests asserts en/zh key parity per plugin at CI time, not just at i18n-load time.
- Forgot-PIN flow (parent generates reset code → kid enters it on the device) has a UX cliff if the parent isn't physically present. Acceptable for a family product but worth flagging — there's no email-based reset for kids.
- Plugin schemaVersion migrate-on-read means a kid mid-attempt with an old session can encounter a plugin version bump. Current design discards the partial silently with a logged warning; this could lose 30 seconds of writing. Confirm acceptable vs implementing registered session migrators (open question).
- View-as-child token: mutations are rejected server-side AND short-circuited client-side. If a third path appears (e.g. an embedded iframe), the rejection is the only backstop. Encode in audit log + add a Playwright test that all known mutation routes return 403 with role='child-readonly'.
- Dropping v1 chat means parents who used it lose a feature. v1 had unauthenticated chat (audit #1.1 blocker) — not a regression worth defending. Communicate clearly in changelog.
